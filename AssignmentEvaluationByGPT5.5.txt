Critical inconsistencies to fix first
1. Phantom Assignment 5 / capstone references

README lists only Assignments 1–4 in the repository layout, ending with Assignment 4 and notebooks.
But the syllabus tells learners to decide whether to take on Assignment 5 and read assignment_05_capstone/ASSIGNMENT.md. Assignment 2 solution notes also mention a “LangChain capstone” / Assignment 5.

What could go wrong: learners will search for a capstone that is not in the visible repo structure and assume files are missing.

Fix: either add the capstone files and README entries, or remove all Assignment 5 references from the syllabus, solution notes, and Makefile.

2. Path typo in syllabus: assignment-04-evals vs assignment_04_evals

The syllabus says to read assignment-04-evals/ASSIGNMENT.md, but the repo layout and commands consistently use assignment_04_evals/.

What could go wrong: copy-paste navigation fails.

Fix: change assignment-04-evals/ASSIGNMENT.md to assignment_04_evals/ASSIGNMENT.md.

3. README says “All scripts print token usage,” but that is not true

README says: “All scripts print token usage. So you can audit the spend at any time.”
Assignment 1 and Assignment 2 do print token/cost or meta usage, but Assignment 3’s RAG answer() / CLI does not track or print OpenAI token usage, and the RAG generator returns only text, citations, and is_grounded.

What could go wrong: learners expect cost observability everywhere, but the RAG and eval layers do not consistently expose it.

Fix: soften README to “Some scripts print token usage,” or add token accounting to Assignment 3 generation and Assignment 4 reporting.

4. Assignment 1 token-count wording contradicts the solution notes

Assignment 1 says local tiktoken counts and API usage.*_tokens “should agree.”
But the hints and solution correctly explain that local counting of message content will usually be slightly under API prompt tokens because API usage includes message overhead; the solution treats “within ~10 tokens” as a match.

What could go wrong: mentees may waste time trying to exactly reverse-engineer Chat Completions token accounting.

Fix: replace “They should agree” with “They should be close; exact agreement is not expected because API usage includes message/role overhead.”

5. Assignment 2 expected extraction conflicts with transcript + system prompt

Assignment 2’s sample JSON lists only Priya, Marcus, and Sofia as attendees.
But the starter system prompt says attendees should include “every distinct person who spoke OR was named as agreeing to a decision.” The transcript names Aisha in a decision (“Aisha takes primary on-call…”), mentions Hiroshi’s leave, and mentions Jamal as the intern Sofia will pair with.

What could go wrong: a good implementation may include Aisha, Hiroshi, or Jamal and appear to disagree with the provided expected output. This especially affects the cross-field validator, because action-item owners must match attendee names, but “attendee” semantics are not stable.

Fix: explicitly define one of these:

Option A: attendees = speakers only; named non-speakers go elsewhere.
Option B: attendees = speakers plus people assigned or affected by decisions.
Option C: attendees = all named employees.

Then align the sample JSON, system prompt, employee directory, and grading expectations.

6. Assignment 2 model-call budget is undercounted

The assignment says the loop is “at most 4 tool-call iterations + 1 retry = 5 model calls total.”
But the flow is actually: up to 4 tool-loop calls, then a final structured-output call, then possibly one retry structured-output call. That can be 6 model calls, not 5.

What could go wrong: cost estimates and debugging expectations are wrong.

Fix: say “at most 4 tool-loop calls + 1 final structured call + 1 retry = 6 model calls.”

7. Assignment 3 reference chunker can violate its own “max chunk size” contract

Starter requirements say each chunk should be at most chunk_size characters.
The reference solution first creates chunks, then prepends overlap from the previous chunk, which can push chunks above chunk_size. I tested the same logic locally against 04-expense-reimbursement.md with chunk_size=500, chunk_overlap=50, and some chunks became >500 characters.

What could go wrong: learners who enforce the stated invariant will differ from the reference solution; learners who copy the reference may fail stricter tests.

Fix: clarify “approximately chunk_size, overlap may make final chunks slightly longer,” or trim/repack after adding overlap.

8. Assignment 4 evaluates the reference RAG, not necessarily the mentee’s RAG

Assignment 4 tells the harness to call assignment_03_rag/solution/.
That is useful for a known-good baseline, but it can mask bugs in the mentee’s own Assignment 3 implementation.

What could go wrong: a mentee’s starter/ RAG can be broken while Assignment 4 evals pass because they are evaluating the provided solution.

Fix: make the target configurable, for example:

--rag-package assignment_03_rag.starter

or explicitly state: “Use solution/ only for the walkthrough; your submitted eval must run against your own Assignment 3 implementation.”

9. Assignment 4 metric names are inconsistent across assignment, solution, tests, and example JSON

Assignment 4 asks pytest to assert recall_at_5 >= 0.85.
The reference run_eval.py instead writes recall_at_{top_k} dynamically, so a top-k=3 run writes recall_at_3, not recall_at_5. The reference tests work around this with dynamic key lookup, but the starter test asks for recall_at_5 directly. Example reports add yet another form: recall_at_3_topk / recall_at_8_topk.

What could go wrong: reports and tests may not agree, especially when comparing top-k=3 vs top-k=8.

Fix: standardize on both:

fixed keys: recall_at_1, recall_at_3, recall_at_5
run key: recall_at_config_k

Avoid keys like recall_at_3_topk.

10. Assignment 4 says “chain-of-thought reasoning” should be emitted

Assignment 4 asks the judge to use “chain-of-thought reasoning” and return {"reasoning": "...", "score": ...}.
For a teaching repo, I’d avoid the phrase “chain-of-thought” and use “brief rationale” or “rubric rationale” instead. The reference code already stores a reasoning field, but it does not need to ask for private-style step-by-step reasoning.

What could go wrong: learners imitate a pattern that is not ideal for production judge design and may produce verbose rationales that increase cost.

Fix: change to: “The judge must provide a concise rubric-grounded rationale before the score.”

Factual / API checks

The hard-coded current pricing for gpt-4o-mini in Assignment 1 is consistent with current official OpenAI model docs: $0.15 input and $0.60 output per 1M tokens. The gpt-4o pricing constants are also consistent with official docs at $2.50 input and $10.00 output per 1M tokens.

The text-embedding-3-small price in the Assignment 3 solution notes—$0.02 per 1M tokens—is consistent with official OpenAI docs.

The use of client.chat.completions.parse(..., response_format=SomePydanticModel) is supported by the official Structured Outputs guide. However, the reference Assignment 4 judge uses client.beta.chat.completions.parse, while the starter comments say OpenAI().chat.completions.parse(...). Both may work depending on SDK version, but the repo should use one style consistently.

Policy corpus issues / edge cases
Expense reimbursement has an ambiguity around 31–60 day submissions

The policy says expenses must be submitted within 30 days, and expenses older than 60 days will not be reimbursed under any circumstance. That leaves a gray zone: what happens to expenses submitted after 30 days but before 60 days?

Likely RAG failure: a model may answer either “not reimbursed” or “late but maybe reimbursable,” depending on which sentence it emphasizes.

Fix: add a rule like: “Expenses submitted 31–60 days late require manager + Finance approval” or “31–60 days are reimbursed only by exception.”

Remote-work and VPN foreign-country rules mostly align, but create a multi-policy edge case

Remote Work allows work from another country for up to 30 days per rolling 12-month period with manager approval, tax/immigration compliance, and core-hour overlap. VPN policy separately allows foreign-country VPN connections for trips up to 30 days but may block restricted countries, requiring a 7-day-advance Security ticket.

Likely RAG failure: for “Can I work from another country for 20 days?” the correct answer may need both Remote Work and VPN policies. A single-source retrieval metric may under-measure this.

Fix: add a gold eval item that expects both 03-remote-work-policy.md and 06-vpn-and-network-access.md.

Equipment loss overlaps with incident response

IT Equipment requires lost/stolen equipment to be reported to IT and Security within 24 hours, plus a police report within 72 hours for stolen equipment. Security Incident Response also treats lost/stolen/unrecoverable equipment as a reportable security incident.

This is not a contradiction, but it is a good multi-hop test. Your gold item already includes this shape, which is good.

Evaluation-design weaknesses
Multi-hop retrieval metric is too lenient

Assignment 4 defines retrieval as correct if at least one expected source appears in top-k. For single-source questions, that is fine. For multi-hop questions with two expected sources, it overstates success: retrieving only one of two required sources still counts as correct.

What could go wrong: a system can score high recall while failing multi-hop answers.

Fix: add a stricter metric:

source_recall@k = |expected_sources ∩ retrieved_sources[:k]| / |expected_sources|
all_sources_hit@k = 1 if every expected source is retrieved else 0

Keep the current metric as “any-source recall,” but do not rely on it alone.

LLM-as-judge may overrate unsupported but plausible answers

The solution notes correctly acknowledge that LLM-as-judge is noisy and biased, and same-model judging can inflate scores. The assignment also tells learners to note the limitation if the same model is used for answering and judging.

Fix: make the example report explicitly include a “known limitation” line when judge_model == chat_model.

Example deliverable says numbers are illustrative, but the JSON filenames look like real reports

The example README says the deliverable files are exemplars and not real run output. The comparison file also says the numbers are illustrative. That is good, but the JSON filenames (eval_baseline_summary.json, eval_large_chunks_summary.json) can still be mistaken for reports.

Fix: rename them to example_eval_baseline_summary.json and example_eval_large_chunks_summary.json.

Recommended fix order
Fix broken references: Assignment 5/capstone, assignment-04-evals, Makefile phantom targets.
Align Assignment 2 semantics: decide what “attendee” means and update expected output, prompt, and directory.
Standardize eval metric keys: especially recall_at_5 vs dynamic recall_at_{top_k} vs recall_at_3_topk.
Correct cost/token wording: “token counts should be close,” not equal; “all scripts” do not print usage.
Tighten Assignment 3 chunking contract: either allow overlap to exceed chunk size or enforce max length after overlap.
Strengthen evals: add all-source recall for multi-hop, citation correctness, and a short same-model judge limitation note.

Overall, this is a solid bootcamp repo. The main risks are not conceptual; they are spec drift and example/reference mismatch, which are exactly the kinds of things that frustrate mentees because their implementation can be reasonable yet appear “wrong.”
